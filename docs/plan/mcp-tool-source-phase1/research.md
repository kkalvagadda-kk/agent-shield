# Research — MCP as a Tool Source, Phase 1

This document covers two kinds of decisions:

1. **Grounding corrections** — facts discovered by reading the *running* code (not the design docs) during planning, that materially change how Phase 1 must be implemented. Numbered continuing from the architecture doc's own §2 list (which stopped at 7).
2. **Implementation-level decisions** the architecture doc left unpinned (module structure, library choice, exact request/response shapes, field semantics, the proxy auth mechanism, the credential-resolution mechanism) — each with alternatives considered and why the chosen option won.

Where the architecture doc (`docs/design/mcp-tool-source-architecture.md`, updated 2026-07-21 with §3b/§3c and the credential-path/STUB/lifecycle decisions) or `docs/decisions.md` (Decisions 15, 27, 28, 29) already settled something, this doc does not re-derive it — it is cited by reference. Where the design doc and this plan's grounding conflict, **the design doc wins on decisions**; this doc records where the *running product* forced a refinement of a design-doc detail (e.g. the proxy resolving credentials via a per-server Secret rather than a direct DB read).

## Part A — Grounding Corrections (continuing the architecture doc's §2 numbering)

### 8. The live OPA enforcement path is `bundle_generator.py` + the checked-in static `opa_policy/agentshield.rego`, NOT `policy_generator.py`'s per-agent Rego

The architecture doc's §2 point 2 says OPA policy generation happens at deployment time via `policy_generator.generate_and_store` reading `AgentVersion.tools`. That is true as a *call site*, but reading the actual code shows `policy_generator.py`'s per-agent Rego (`package agentshield.agent.{name}`) is **legacy and inert at runtime**: its own docstring says the per-agent ConfigMap write is a no-op since Phase 9.1. The row it writes to `agent_policies` is kept only as an audit/history artifact — nothing serves it to an OPA sidecar.

The system that actually authorizes every tool call today is:
- `services/registry-api/opa_policy/agentshield.rego` — one **static**, checked-in Rego file (`package agentshield`), shared by every agent's OPA sidecar.
- `services/registry-api/bundle_generator.py::generate_bundle_data()` — builds the **data** (`data.agents[sa_subject]`, `data.grants[team]`) the static policy evaluates against, live, on every request.
- `services/registry-api/routers/bundle.py` — serves `GET /api/v1/bundle/bundle.tar.gz` (data.json + policy.rego), regenerated on every poll. OPA sidecars poll every 30–60s.
- `sdk/agentshield_sdk/opa_client.py::check_tool()` — the client every tool call goes through; POSTs to `/v1/data/agentshield` and reads back `{allow, require_approval, reason, deny_reason}`.

**Consequence for Decision 27's `allow_deanonymize` field:** thread it through this real pipeline — `bundle_generator.py`'s per-tool dict emission (both the `agents[sa_subject].tools` list and the `grants[team]` list) and the static `agentshield.rego`'s rule set (mirroring how `risk`/`require_approval` are already computed) — **not** through `policy_generator.py`'s per-agent Rego. `policy_generator.py` is touched only as an optional audit-parity update (the design doc §6a keeps it in parity for its own DB-row inspection purpose); it is **never** the enforcement path and a task must not treat it as one. This is the single most important grounding correction for the OPA half of this plan.

### 9. `opa_decisions` (the audit log FR-MCP-24 requires) has zero writers today, for any tool type

`services/registry-api/routers/opa_decisions.py` exposes `POST /api/v1/opa-decisions/` with a docstring claiming it is "Called by the OPA sidecar after every policy evaluation." That is aspirational — a stock OPA sidecar cannot make an outbound callback after evaluating a query, and nothing in this tree calls the endpoint. The table exists, the query side (`GET`) is real, but the write side is orphaned. **This is true for native/http/python tools today, not just MCP.**

**Naming coincidence, not a relationship:** `services/registry-api/models.py`'s ORM class for this audit table is also named `OPADecision` — same name as the unrelated `sdk/agentshield_sdk/opa_client.OPADecision` dataclass this plan extends with `allow_deanonymize`. Different services, import graphs never cross. Do not conflate them: Task 9 touches the SDK dataclass; Task 11's `record_decision()` constructs a payload for the registry-api endpoint that server-side instantiates `models.OPADecision`.

FR-MCP-24 says an MCP tool call must write an audit record "same as native tools" — but native tools don't either. **Decision: (b)** — add the write generically at the `governed_tool` seam Decision 27 is already editing (right after `check_tool()` returns), for all four tool types, best-effort (never raises — an audit-write failure must not block or falsely allow a call). This turns a currently-false platform claim into a true one and is the "fix the class, not the instance" instinct the constitution calls for. Folded into Task 11 as a `record_decision()` call. Task 17's regression sweep confirms a *native* tool call now also produces an `opa_decisions` row (proving the fix is generic).

### 10. `AgentVersion.tools` has two snapshot sites for sandbox, and a third, weaker path for production

Two call sites build the `{name, risk}` tools list that reaches `bundle_generator.py`'s `agents[sa_subject].tools`:
- `services/registry-api/routers/versions.py` (~L93) — `{"name": t.name, "risk": t.risk_level or "low"}`, from a live `Tool` join (new `AgentVersion` mint).
- `services/registry-api/routers/deployments.py` (~L505) — the same shape, same live join (sandbox deploy).

Both must also carry `"pii_deanonymize_allowed": bool(t.pii_deanonymize_allowed)` (Task 9), or a tool's de-anonymize permission never reaches the sandbox OPA bundle.

**Production is different and weaker.** `bundle_generator.py`'s production leg reads `PublishedVersion.config_snapshot['tools']`, copied verbatim from `AgentVersion.config_snapshot` (`routers/catalog.py`), whose `'tools'` key comes from a client-authored `agent.metadata_['tools']` mirror — **not** a live `Tool` join. This is a **pre-existing parity gap** (tracked in `docs/design/sandbox-production-parity-architecture.md`) that already affects `risk_level` today. **Decision:** Phase 1 does **not** fix it — logged in the gap ledger as "pre-existing, not deepened." `allow_deanonymize` (like `risk`-driven `require_approval` already) may be stale in a **production** bundle whose `metadata.tools` mirror is stale. Sandbox is unaffected (live join). Called out rather than silently narrowing FR-MCP-51/52's scope.

### 11. The baseline moved: migration head is `0071` (not `0068`), image tags advanced — chain/verify from the running product

The design doc and the earlier draft of this plan said "latest migration is 0068, new migration is 0069." Reading the actual `alembic/versions/` tree: there is **no `0069`** (a former `0069` was superseded and renumbered), the head is **`0071`** (`0071` → `down_revision 0070` → `0070` down_revision `0068`). Therefore this plan's migration is **`0072`, `down_revision = "0071"`** (data-model.md). Likewise the current image tags are `REGISTRY_API_TAG=0.2.224`, `STUDIO_TAG=0.1.160`, `DECLARATIVE_RUNNER_TAG=0.1.59`, `SAFETY_ORCHESTRATOR_TAG=0.1.3`, `DEPLOY_CONTROLLER_TAG=0.1.40`, `PYTHON_EXECUTOR_TAG=0.1.0`, `sdk.__version__=0.2.0` — all higher than the earlier draft assumed. Per the constitution's "reason from the running product," every task's tag bump and the migration number are relative to whatever `quickstart.md`'s verify-first commands report at implementation time; the numbers here are the observed baseline, not a hardcode.

### 12. registry-api already has K8s Secret CRUD (`k8s.upsert_secret`/`delete_secret`) + `crypto.decrypt_json`, and a cluster-wide secret ClusterRole — so per-server Secret materialization needs no new K8s or RBAC code in registry-api

`services/registry-api/k8s.py` already exposes `upsert_secret(name, namespace, data)` (create-or-replace), `secret_exists(name, ns)`, and `delete_secret(name, ns)`. `services/registry-api/crypto.py` exposes `decrypt_json(token) -> dict` and `encrypt_json(data) -> str`, keyed on `AGENTSHIELD_ENCRYPTION_KEY` (which registry-api already holds via a `secretKeyRef` in its Deployment). `routers/auth_configs.py` already proves the exact pattern this plan reuses: on create it writes both the durable `credentials_encrypted = encrypt_json(body.credentials)` **and** a runtime Secret `auth-config-{id}` in `agentshield-platform`; `GET /auth-configs/{id}/secret-ref` re-materializes a missing Secret from the durable copy. registry-api's Helm RBAC is a **ClusterRole** granting `create/get/update/patch/delete` on `secrets` cluster-wide (`charts/agentshield/charts/registry-api/templates/rbac.yaml`). **Consequence:** Task 3's per-server Secret materializer is a thin composition over `crypto.decrypt_json` + `k8s.upsert_secret`/`delete_secret` — **no new registry-api K8s client code and no new registry-api RBAC** (the existing cluster-wide secret verbs already cover writing into the new `agentshield-mcp` namespace).

### 13. `governed_tool` today has no per-tool-call output scan or de-anonymize for any type — the once-per-turn scan lives in `runner.py`

Grep confirms `sdk/agentshield_sdk/graph_builder.py`'s `governed_tool` (the wrapper every tool call crosses) calls `opa_client.check_tool` and `require_approval` but **never** `scan_output`/`scan_input`/de-anonymize. The existing safety scan is once-per-turn, in `sdk/agentshield_sdk/runner.py` (`scan_input` before the graph, `scan_output` after — lines ~109/141/250). Decision 27's per-tool gate (Task 11) is therefore genuinely new code at the `governed_tool` seam, not a modification of an existing per-tool scan. This also means the mandatory regression sweep (Task 17) is required precisely because Task 11 adds a scan call to a path that had none, for *every* tool type.

### 14. The `safety_client` field bug is in BOTH the request and the response — and the request half means scans currently fail-closed in a real deployment

`services/safety-orchestrator/schemas.py` defines `ScanOutputRequest{session_id, agent_name, message, thread_id}` and `ScanOutputResponse{allowed, blocked, reason, deanonymized_message, scores}` (and the `ScanInput*` analogues with `anonymized_message`). But `sdk/agentshield_sdk/safety_client.py` sends `{"text", "agent_name", "session_id", "trace_id"}` and reads `data.get("clean_text")` / `data.get("sanitized_text")`. Two independent mismatches:
- **Request:** SDK sends `text` (server wants `message`) and `trace_id` (server wants `thread_id`); `message` is a *required* field, so the server 422s → `resp.raise_for_status()` raises → caught → `SafetyBlockedError(reason="scanner_error")`. In other words, with `AGENTSHIELD_SAFETY_URL` set, **every** `scan_output`/`scan_input` currently fails closed. (The design doc §2.3 noticed only the response half; reading the schema exposes the request half too.)
- **Response:** even if the request were right, the SDK reads `clean_text`/`sanitized_text` which the server never sends — it sends `deanonymized_message`/`anonymized_message` — so the de-anonymized text is discarded.

**Fix (Task 10):** in `safety_client.py`, change the request payload keys (`text→message`, `trace_id→thread_id`) for both `scan_input` and `scan_output`, and change the response reads (`sanitized_text→anonymized_message`, `clean_text→deanonymized_message`) with the same original-text fallback. **Keep** the SDK-side dataclass field names `ScanInputResult.sanitized_text` / `ScanOutputResult.clean_text` unchanged — those are the SDK's public contract to `runner.py`/`graph_builder.py`; only what the client *sends to* and *reads from* the server changes. Live consumer proving the fix isn't orphaned: `runner.py`'s once-per-turn `scan_output`/`scan_input` (independent of anything MCP). Regression-test-first per constitution rule 7 (a test that fails against the buggy code first — Task 10).

### 15. An agent pod's SA subject encodes its team in the namespace (`agents-{team}`) — the proxy derives caller-team without a DB read

Agent pods run in per-team namespaces `agents-{team}` (`deployments.py::_derive_k8s_namespace`; `AgentIdentity.sa_namespace`), and their projected SA token's subject is `system:serviceaccount:agents-{team}:{sa}`. So the MCP Proxy, after verifying a caller's token via TokenReview, derives `caller_team` by string-parsing the namespace segment of the subject (strip the `agents-` prefix) — **no DB lookup** for the common "own-team" authz path (see B12). The proxy 403s any subject whose namespace does not match the `agents-` form (defense-in-depth; production-namespace naming is confirmed at build — gap-ledgered).

## Part B — Implementation-Level Decisions

### B1. MCP protocol client library: the official `mcp` Python SDK

**Chosen:** `mcp` (the reference Model Context Protocol Python SDK), specifically `mcp.client.streamable_http.streamablehttp_client` (async context manager yielding read/write streams) + `mcp.ClientSession` (`.initialize()`, `.list_tools()`, `.call_tool(name, arguments)`), and `mcp.server.fastmcp.FastMCP` for the e2e fixture (Task 15, B10).

**Alternatives:** hand-rolled httpx + manual JSON-RPC (rejected — `streamable_http` has real protocol behavior: session negotiation, SSE-vs-plain-JSON responses, capability negotiation during `initialize`; re-implementing it inside the proxy defeats the proxy's reason to exist); a community MCP client (rejected — the official SDK is maintained by the protocol's stewards).

**Pin:** `services/mcp-proxy/requirements.txt` pins `mcp>=1.2,<2.0`; verify the latest stable minor at implementation time via `pip index versions mcp` (quickstart.md) — do not silently jump a major. The wire schema uses camelCase `inputSchema`, exposed as `.inputSchema` on the SDK's `types.Tool` model; re-verify attribute names against the installed version during Task 5.

### B2. MCP Proxy internal module structure

The proxy is stateful (live sessions) and now also a security boundary (TokenReview AuthN, coarse AuthZ, credential custody), so — unlike `python-executor`'s single `main.py` — it splits by concern:

```
services/mcp-proxy/
  main.py           — FastAPI app; /health, /ready, /internal/discover, /internal/tools/call
  config.py         — env vars (REGISTRY_API_URL, PORT, audiences, SA names, cache TTLs, MCP_SECRETS_NAMESPACE)
  schemas.py        — pydantic request/response models (contracts/mcp-proxy-internal.md, design §3c)
  mcp_client.py     — wrapper over mcp.client.streamable_http + mcp.ClientSession: connect_and_initialize(), list_tools(), call_tool(), close()
  session_cache.py  — per-replica in-memory {server_id: CachedSession}; get_or_create + evict-on-error
  k8s_client.py     — in-cluster kubernetes client: read_namespaced_secret (MCP_SECRETS_NAMESPACE) + create_token_review; mirrors registry-api/k8s.py _init_k8s() but READ-ONLY + AuthN
  authn.py          — verify_bearer_token(token) -> sa_subject | None via TokenReview (audience gate) + positive-review cache keyed by sha256(token) until the token's exp
  authz.py          — team_from_sa_subject(sa_subject); authorize_tool_call(caller_sa_subject, server_id, mcp_tool_name, owner_team) -> bool (own-team fast path; registry-api callback for cross-team)
  credentials.py    — read_server_secret(server_id) -> ServerConnection{server_url, transport, transport_config, is_external, owner_team, auth_headers} from the per-server K8s Secret
  Dockerfile        — python:3.12-slim, mirrors python-executor/Dockerfile
  requirements.txt  — fastapi, uvicorn[standard], pydantic, httpx, kubernetes, mcp  (NO sqlalchemy/asyncpg — the proxy never touches the DB)
```

**Alternative:** one flat `main.py`. Rejected — `python-executor` has no state, no auth, no outbound dependency; the proxy has all three, and separating "verify a token," "decide team access," "resolve credentials," and "speak MCP" now keeps Phase 2/3 additions (health loop, per-server-pod routing) local to one module each.

### B3. MCP Proxy resolves server connection + credentials from a per-server K8s Secret — it never reads the DB and never holds the global encryption key (refines design §3c's "own DB read")

The design doc §3c says the proxy resolves `server_id → url/transport/credential` via its "own read-only DB read of `mcp_servers`/`auth_configs`." Read literally that hands the proxy a Postgres connection and read access to credential tables — which cuts directly against §3b's own least-privilege framing ("proxy SA gets `system:auth-delegator` and nothing broader") and against the credential-path-(b) decision (keep the proxy off `AGENTSHIELD_ENCRYPTION_KEY`). The brief explicitly delegates the "shared-lib vs. internal-endpoint / how the proxy resolves" call to this plan. **Decision: the proxy does NOT read the DB.** It reads exactly one thing per server — the per-server K8s Secret (B13) that registry-api materialized at register/sync — which carries both the connection metadata and the ready-to-use auth headers:

- On a cache miss for `server_id`, `credentials.read_server_secret(server_id)` does a single `read_namespaced_secret("agentshield-mcp-server-{server_id}", MCP_SECRETS_NAMESPACE)` and parses its `connection` (JSON: `server_url`, `transport`, `transport_config`, `is_external`, `owner_team`) and `auth_headers` (JSON: header→value). No httpx call to registry-api, no DB, no decryption (registry-api already decrypted at materialization).
- The parsed `ServerConnection` + the live `ClientSession` are cached per `server_id` in `session_cache.py`. A `tools/call` auth error (401/403 from the upstream server) evicts the cached session and re-reads the Secret once (covers a credential rotation, which re-materializes the same-named Secret's contents).

This is strictly less privilege than §3c's literal reading: the proxy needs only `get` on Secrets in one dedicated namespace (B13) and never touches the DB or the master key. It is documented as a refinement of §3c, justified by §3b's own least-privilege principle, in data-model.md and the design doc's §8 ("Shared `team_may_use_tool`" / "authz-floor" rows).

### B4. `Tool.pii_deanonymize_allowed` — a new per-tool boolean column, not an overload of `risk_level`

De-anonymization (should a tool receive **real PII** in its arguments) is orthogonal to risk (may this call execute / does it need approval). Piggy-backing it on `risk_level` — already driving `allow`/`require_approval` — is the exact implicit-coupling the constitution warns against. **Decision:** add `Tool.pii_deanonymize_allowed: bool NOT NULL DEFAULT false`, mirroring the existing precedent `Tool.side_effecting` (migration 0063): a second orthogonal per-tool boolean, fail-closed default, exposed in `ToolCreate`/`ToolUpdate`/`ToolResponse`, carried onto the resolved callable, threaded into `bundle_generator.py`/Rego the same way `risk` is. "Same risk-driven generation path" (FR-MCP-51) is satisfied at the *mechanism* level (same bundle → same static Rego → same OPA response schema), not by reusing `risk_level`'s value. Default `false` = no tool receives real PII unless an admin marks it trusted.

### B5. The structured de-anonymize primitive substitutes locally from cached PII mappings — it does not call Presidio's `/deanonymize`

`services/safety-orchestrator/pii_store.py`'s `PiiMapping` rows already carry both `anonymized_text` (the placeholder Presidio minted, e.g. `<PERSON_0>`) and `original_text`. **Decision:** the new `Orchestrator.deanonymize_args` does a **local recursive string replace** — for every mapping row for `(session_id, agent_name)`, replace each literal `anonymized_text` with `original_text` inside every string leaf of the args dict (recurse dicts/lists; non-strings pass through). It does **not** call Presidio's HTTP endpoint. Why: the substitution is a pure string op once mappings are in hand; it stays available even if Presidio is down but Postgres is up (appropriate for best-effort enrichment, B6); and it avoids Presidio's free-text `/deanonymize` request shape, which was not designed for a nested JSON args tree.

### B6. De-anonymize failure is fail-open (proceed with placeholders); output-scan failure stays fail-closed *by the client*, but the ACTION is a Phase-1 STUB

`scan_output`/`scan_input` remain fail-closed **in the client** (`safety_client` raises `SafetyBlockedError` on unreachable/blocked). The **new** de-anonymize-args step is deliberately narrower: if it fails (orchestrator unreachable or the endpoint errors), `governed_tool` logs a warning and proceeds with the **original, still-anonymized** args — a *functional* degradation (the tool may do the wrong thing), not a *security* regression (less real data reaches the tool, nothing unsafe is exposed). Fail-closing here would block every PII-carrying call on any orchestrator hiccup, a much larger blast radius for a smaller benefit. This asymmetry is stated so a future reader does not "fix" it by making both paths fail-closed. **Crucially (B14):** the *output-scan* step's block/redact **action** is stubbed in Phase 1 — the client-side fail-closed *reachability* posture is retained (a broken scanner is still logged), but a *blocked verdict* on a reachable scanner is logged and NOT enforced. See B14.

### B7. Output-scan reuses the existing `scan_output` (including its free-text de-anonymize side-effect) per tool result — known low-probability edge

Reusing `scan_output` per tool call means the existing free-text de-anonymize inside `_scan_output_inner` also runs on each tool result, which could substitute a real PII value into text re-entering the LLM context if a tool echoes back one of its own input placeholders verbatim — a narrow edge that already exists identically for the once-per-turn case. This plan does not add a "skip de-anonymize when per-tool" mode (a new parameter threaded through an endpoint whose only other caller doesn't need it, for a narrow edge). Because the output-scan ACTION is a STUB in Phase 1 (B14) and the scan's transformed text is **not** returned to the LLM (the raw tool result is), this edge is *further* de-risked in Phase 1 — but it is still ledgered as a known, low-probability, pre-existing-shaped risk to revisit when the action is made real.

### B8. Env var naming and token paths

Two conventions are in active use: SDK/runner cross-service URLs prefix `AGENTSHIELD_` (`AGENTSHIELD_SAFETY_URL`, `AGENTSHIELD_OPA_URL`); registry-api outbound clients are unprefixed (`EMBEDDING_SIDECAR_URL`, and declarative-runner's own `PYTHON_EXECUTOR_URL`/`REGISTRY_API_URL` are unprefixed). **Decision — follow the majority on each side:**
- SDK: `AGENTSHIELD_MCP_PROXY_URL` (default `http://agentshield-mcp-proxy.agentshield-platform:8080`) in `sdk/agentshield_sdk/config.py`, plus `AGENTSHIELD_MCP_PROXY_SA_TOKEN_PATH` (default `/var/run/secrets/mcp-proxy-token/token`) mirroring the existing `AGENTSHIELD_SA_TOKEN_PATH` for the OPA token.
- declarative-runner: `MCP_PROXY_URL` (unprefixed, matching its sibling `PYTHON_EXECUTOR_URL`) + `MCP_PROXY_SA_TOKEN_PATH` in `services/declarative-runner/config.py`.
- registry-api: unprefixed `MCP_PROXY_URL` (default `http://agentshield-mcp-proxy.agentshield-platform.svc.cluster.local:8080`) in `services/registry-api/mcp_proxy_client.py`, matching `embedding_client.py`'s host format, plus `MCP_PROXY_SA_TOKEN_PATH` for the audience-scoped token it presents to `/internal/discover`.

Do not invent a third pattern.

### B9. Studio: MCP servers get their own `mcpServersApi.ts`, not additions to `registryApi.ts`

Knowledge Bases (the closest precedent) has its own `knowledgeApi.ts` riding the shared `http` axios instance from `registryApi.ts`. MCP servers are a distinct resource (register/sync/delete) unrelated to `Tool` CRUD, so this plan creates `studio/src/api/mcpServersApi.ts` importing `http` from `registryApi.ts`. `RegistryTool` (in `registryApi.ts`) still gains the new optional fields it needs (`mcp_server_id`, `mcp_tool_name`, `mcp_server_name`, `mcp_server_is_external`, `mcp_server_scan_results`, `pii_deanonymize_allowed`) because those describe a `Tool` row — only the *server* resource gets a new file.

### B10. Fixture MCP server runs inside the MCP Proxy pod, using the same `mcp` SDK

`scripts/e2e/fixtures/stub_mcp_server.py` is a small `mcp.server.fastmcp.FastMCP` script (`transport="streamable-http"`) copied into the `mcp-proxy` image (`COPY scripts/e2e/fixtures/stub_mcp_server.py /app/fixtures/`) and started via `kubectl exec ... python3 fixtures/stub_mcp_server.py &` inside the running `mcp-proxy` pod on `127.0.0.1:9999` — never auto-started by `main.py`, so it is inert in a normal deployment. Because it shares the proxy's network namespace, registering an `MCPServer` with `server_url=http://127.0.0.1:9999/mcp` lets the proxy dial a real, protocol-compliant server with **no new cluster object**. It exposes `echo(text: str) -> str` (verbatim — proves de-anonymize substitution) and `add(a: int, b: int) -> int`. Flagged test-only in the suite header. Alternative (a standing K8s Job/Deployment fixture) rejected for Phase 1 — permanent object + Service/DNS for one suite, when the in-pod approach gets full protocol coverage for zero new infra.

### B11. De-anonymize runs immediately before the *real* dispatch, strictly after the eval-record short-circuit

The gate order "authorize → approve → de-anonymize → execute → scan" (design §3), read literally, would place de-anonymize before `governed_tool`'s eval-mode short-circuit (`_should_record(fn)` / `_record_side_effect`), which under `eval_mode=record` never calls the real `fn` — it records args and returns a mock. If de-anonymize ran first, a real-PII-containing kwargs dict would be persisted into the eval trace (a third PII destination FR-MCP-30 never considered). **Decision:** place de-anonymize *inside* the "Deliver" branch, **after** the `_should_record(fn)` early-return and **immediately before** the real `fn(**kwargs)`. This satisfies "de-anonymize → execute" literally while ensuring de-anonymize never runs on a call eval-mode will mock. Task 11 implements it at this exact point.

### B12. Proxy AuthN = K8s TokenReview + positive-review cache; AuthZ = own-team fast path + an authenticated-by-network internal registry-api endpoint (NOT a shared cross-service library)

**AuthN.** The proxy verifies each inbound `Authorization: Bearer <token>` via K8s `TokenReview` (`AuthenticationV1Api.create_token_review` with `spec.audiences=["agentshield-mcp-proxy"]`), checks `status.authenticated` **and** that `status.audiences` contains `agentshield-mcp-proxy`, and extracts `status.user.username` = `system:serviceaccount:<ns>:<sa>`. Positive reviews are cached keyed by `sha256(token)` until the token's `exp` (parsed from the JWT payload the same base64url way `opa_client._parse_sa_subject` already does) — no K8s API hit per call. This reuses the one real minted credential the platform already has (the projected SA token OPA uses); the proxy's SA gets `system:auth-delegator` (TokenReview) and nothing broader. Missing/invalid/wrong-audience → `401`.

**AuthZ (coarse team-scope floor).** Defense-in-depth only — OPA already ran the fine-grained per-call decision inside `governed_tool` before the proxy is reached; this floor only stops a pod that *bypassed* `governed_tool`. Steps: derive `caller_team` from the SA subject's `agents-{team}` namespace (B15, no DB); read the per-server Secret's `owner_team` (B3, no DB); **fast path** — if `caller_team == owner_team`, allow with zero further work; **cross-team** — call registry-api `POST /api/v1/internal/mcp/authorize-tool-call {caller_sa_subject, server_id, mcp_tool_name}` which returns `{allowed: bool}`. Cache the cross-team decision per `(caller_sa_subject, server_id, mcp_tool_name)` with a short TTL. `/internal/discover` is admin-plane: the caller's subject must equal registry-api's SA, else `403` (no team floor).

**Why an internal endpoint, not a shared library (the brief's explicit choose-and-justify point).** The grant check *must* be one implementation reused from the deploy gate. The two candidates:
- *Shared library:* the proxy imports a `team_may_use_tool` function that runs SQLAlchemy queries — which forces a DB connection into the proxy **and** either duplicating registry-api's ORM models into the proxy or forking to raw SQL. Raw-SQL-in-proxy vs. ORM-in-registry-api is then **two** implementations of the same rule, defeating "one implementation," and the DB connection re-widens the proxy's blast radius exactly where §3b is trying to narrow it. The design doc §8 recommends "the shared helper (no per-call hop)," but that recommendation assumes the proxy already reads the DB (§3c's literal reading), which B3 rejects on least-privilege grounds.
- *Internal endpoint (chosen):* extract `team_may_use_tool(db, team, tool_id) -> bool` once **inside registry-api** (Task 3), call it from **both** the deploy gate (`deployments.py`, refactor) **and** a thin `POST /api/v1/internal/mcp/authorize-tool-call` (Task 3). The proxy calls that endpoint only on the *cross-team* path — the common own-team path is answered locally with zero hops. "One implementation" is literally satisfied (the function lives in one place; the endpoint and the deploy gate both call it), the proxy needs no DB and no ORM copy, and the per-call-hop cost the §8 recommendation worried about is avoided for the overwhelmingly common own-team case and short-TTL-cached for the rest. The endpoint is unauthenticated / NetworkPolicy-trusted, consistent with every other internal registry-api-facing call (it returns a boolean, never a secret or a URL) — so it does not require registry-api to also run TokenReview.

### B13. Credential path (b): a per-server K8s Secret in a dedicated `agentshield-mcp` namespace; the proxy's RBAC is scoped to that namespace so it can never read the master key

Path (b) is locked by the design doc. Mechanism:
- **Name & namespace:** `agentshield-mcp-server-{server_id}` in a **dedicated namespace `agentshield-mcp`** (created by the mcp-proxy subchart). A dedicated namespace is what makes "narrow read-only RBAC scoped to those Secrets" (design §3b) actually achievable — K8s RBAC cannot filter `get secrets` by name prefix or label, only by namespace or exact `resourceNames`, and the Secret names are dynamic. If the per-server Secrets lived in `agentshield-platform`, a namespace-wide `get secrets` would let the proxy read `agentshield-encryption` (the master Fernet key) and the DB creds — which would make path (b) *worse* than path (a). The dedicated namespace prevents that: the proxy's `Role` grants `get` on `secrets` in `agentshield-mcp` only.
- **Writer:** registry-api's `mcp_servers` router (Task 6), on register / `/sync` / auth-config PUT, calls `mcp_secrets.materialize_server_secret(db, server)` (Task 3) which — if `server.auth_config_id` is set — loads the `AuthConfig`, `crypto.decrypt_json(auth_config.credentials_encrypted)`, composes an `auth_headers` dict from the plaintext creds by `AuthConfig.type` (`bearer` → `{"Authorization": "Bearer <token>"}`; `api_key` → the header name/value in the creds dict; `oauth2`/`mtls` → best-effort, ledgered), and `k8s.upsert_secret("agentshield-mcp-server-{id}", "agentshield-mcp", {"connection": json(...), "auth_headers": json(...)})`. A server with no `auth_config_id` still gets the Secret with `auth_headers: {}`. registry-api's existing cluster-wide secret ClusterRole already permits writing cross-namespace (grounding #12), so **no new registry-api RBAC**.
- **Lifecycle:** deleted via `mcp_secrets.delete_server_secret(server_id)` when the server is deleted (Task 6 DELETE); re-materialized on auth-config change (Task 6 PUT). Secret is a *derived* artifact — the durable source stays the Fernet blob in Postgres.
- **What the proxy holds:** only `get secrets` in `agentshield-mcp` + `system:auth-delegator` for TokenReview. Never `AGENTSHIELD_ENCRYPTION_KEY`, never the DB.

**Alternative (a) — proxy decrypts the Fernet blob directly** (as `judge.py` does for LLM creds): rejected by the design doc because it hands the proxy the master key that decrypts *every* credential in the DB. **Alternative — reuse the AuthConfig's own base Secret `auth-config-{id}` in `agentshield-platform`** (which registry-api already writes): rejected because scoping the proxy to read `agentshield-platform` secrets by name is not expressible in RBAC, so the proxy would again be able to read the master key. The dedicated per-server Secret in a dedicated namespace is the only option that delivers path (b)'s stated benefit.

### B14. The output-scan ACTION is a Phase-1 STUB — verdict computed + logged, never enforced

Decision (design §3 step 6 / §6a / §8, dated 2026-07-21): Phase 1 **wires the per-tool-call `scan_output`** into `governed_tool` and **computes + logs the verdict**, but the **block/redact action on a flagged result is NOT enforced** — deferred to the future safety-orchestration build. Concretely (Task 11): after the real `fn(**kwargs)`, if `getattr(fn, "scan_results", True)` is true, call `scan_output(str(result), ...)` inside a `try/except SafetyBlockedError`; on a blocked verdict (or scanner error) **log** `"output-scan verdict=blocked reason=... (STUB — not enforced)"` and **return the original `result` unchanged**; on a clean verdict, log the scores and **return the original `result`** (the scan's transformed `clean_text` is intentionally discarded in Phase 1 — swapping it in would itself be an "action," and discarding it also side-steps B7). A one-line breadcrumb comment goes in `services/safety-orchestrator/orchestrator.py`'s `scan_output` **and** at the `governed_tool` call site, cross-referencing this decision and the gap ledger. This is ledgered **not-yet-wired (debt)** and **must not be reported done** until the action is real. The scan is still worth wiring now: it proves the seam, produces the verdict/scores for logging + the (automatic) Langfuse span, and — because the same `scan_output` client is used by `runner.py`'s once-per-turn path — Task 10's field-bug fix has a live, non-MCP consumer regardless of the stub.

### B15. `is_external` forces the scan-call ON even when the stub can't act; `scan_results` only opts an internal server out of the (stubbed) call

`governed_tool` decides whether to *call* `scan_output` per B14 using the resolved `fn.scan_results` attribute: `True` if the owning server `is_external` (external results always scanned — FR-MCP-31), else the server's `scan_results` flag (internal opt-out). Because the *action* is stubbed, this flag governs only whether the scan *call + logging* happens in Phase 1, not whether anything is enforced — but wiring it correctly now means the eventual un-stubbing needs no dispatch change. The SDK/runner compute `scan_results` at executor-build time: `scan_results = True if mcp_server_is_external else bool(mcp_server_scan_results)` (Key Interfaces in plan.md).
