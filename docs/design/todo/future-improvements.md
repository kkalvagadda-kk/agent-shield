1. **Traffic splitting / canary support** — split traffic % between two deployments of the same artifact on a shared endpoint. Enables gradual rollout without separate URLs.
2. **Deployment event log** — live stream of infra events alongside the overview (pulling image, creating pods, health check passed/failed, scaling events). Makes status transitions visible to the user rather than opaque badge changes.
3. **Blue-green rollback** — one-click rollback to previous version using `previous_version_id`. Drain in-flight requests before terminating old deployment.
4. **Run 2 versions side-by-side live (Playground version compare)** — in the Playground, enter a comparison mode, send one prompt, and run it against two agent versions *in parallel*. Show both outputs, trace depth, and token/cost deltas side by side, so a developer can judge a version bump without leaving Studio. This is the *live* counterpart to the already-shipped post-hoc trace compare (`ObservabilityComparePage.tsx`, reachable via Traces → select 2 → Compare), which only diffs two runs that already happened. Here both runs are fired on demand from the same prompt.

## MCP-as-tool-source — pending from the original roadmap

The core is shipped and **cluster-proven on EKS**: Phase 1 (register → discover → bind → governed execute), Phase 2 (health loop, `notifications/tools/list_changed` subscription, `service_identity`), and Phase 4 (OAuth 2.1 + pluggable `CredentialProvider`), including real end-to-end runs against DeepWiki (no-auth), Tavily (bearer), and GitHub/Linear (OAuth). The items below were in the original plan (`docs/design/todo/mcp-tools-for-agents-requirements.md` §11; gap ledger in `docs/design/mcp-tool-source-architecture.md` §8) and are **not yet built**.

5. **stdio transport + supply-chain hardening (Phase 3).** *deferred (intentional) — largest missing capability.* Only `streamable_http` is supported; the schema **422-rejects `transport=stdio`** and Studio grays it out. stdio unlocks the whole `npx`/`uvx` local-server ecosystem (D2), but is the heaviest to secure — SR-01 requires each stdio server to run in a locked-down sandbox **inside the proxy** (read-only rootfs, dropped capabilities, no host network unless granted, CPU/mem limits) plus an **admin-approved command allowlist** (not free-text from any operator), egress policy, and SSRF validation (SR-04/05). None of this exists. Note the proxy is already stateful (holds live sessions), so stdio adds subprocess lifecycle + reconnect-on-restart on top of the sandbox work.

6. **On-behalf-of identity for internal servers (FR-MCP-21, Phase 2 WS-C).** *blocked on an external dependency (Decision 29).* For an internal MCP server with `identity_mode=on_behalf_of`, the proxy should present the **calling user's** identity so the server enforces per-user authz. It is a **fail-closed stub** today (`OnBehalfOfNotAvailable` — never silently downgrades to service-identity). Hard-blocked on `docs/design/identity-propagation-architecture.md` (Proposed, unbuilt): no re-presentable user access token survives past `auth_middleware.py` — only a derived `user_sub` string — so it must be **Keycloak impersonation-based token exchange** (a confidential MCP-proxy client with an impersonation grant mints a token *for* `RunContext.user_sub`), not RFC 8693 subject-token exchange. Once the identity-propagation Phase 0–2 lands, the MCP-specific work is: (1) the confidential Keycloak client + impersonation grant; (2) `governed_tool`'s `mcp_tool` branch includes `user_sub` in the `/tools-call` request only when `identity_mode == on_behalf_of`; (3) proxy performs the impersonation exchange per call; (4) fail-closed on empty `user_sub`. (`service_identity` — FR-MCP-22 — **is** built and proven.)

7. **MCP `resources` & `prompts` primitives (Phase 5 / OQ-02).** *deferred (intentional).* Agents consume only the `tools` primitive. MCP servers can also expose **resources** (files/data an agent can read) and **prompts** (server-provided prompt templates). Neither is discovered or consumed — split out to a distinct primitive subsystem (Phase-4 plan WS-3 sketch). Sequence it if a target server has must-have resources/prompts.

8. **Decision-27 output-scan *enforcement*.** *not-yet-wired (debt) — audit-only today.* The per-tool-call governance gate (`governed_tool`) computes and **logs** the output-scan verdict but does **not** enforce block/redact — it is a STUB mirroring the STUB in `safety-orchestrator/orchestrator.py`. The PII **de-anonymize** side works; enforcement (block/redact a tool result) is deferred to a future safety-orchestration build. **Must never be reported as "output scanning enforced."**

9. **AWS Secrets Manager credential backend (Decision 31, WS-1).** *deferred (intentional) — seam built, backend unproven.* `CredentialProvider` is pluggable; `FernetPgProvider` (encrypted blob in Postgres) is the live default and only a **ref** lives in the DB. `AwsSecretsManagerProvider` is coded and opt-in (`CREDENTIAL_PROVIDER_BACKEND=aws-sm`, lazy boto3, IRSA), but is **not deployed or cluster-tested**. The evolution target (move durable secrets off the single master `AGENTSHIELD_ENCRYPTION_KEY` into an external secret store) is the point of the seam.

**Smaller deferred items (gap ledger):**
- **SSRF / egress validation** on `server_url` (SR-04/05) — a registered URL is not validated against internal-network SSRF; the proxy will dial whatever it's given.
- **Discovery pagination / backpressure** for servers with large tool sets (GitHub already returns 44).
- **OAuth revoke latency** (~30s): the proxy caches the access token and has no registry-api→proxy invalidation channel, so a revoked grant fails closed only after the upstream 401 + `MCP_CONNECT_TIMEOUT_SECONDS`. A proactive invalidation call on `DELETE …/oauth` would make it instant.
- **OAuth scope breadth**: authorize requests **all** of the resource's advertised scopes (RFC 9728 `scopes_supported`) — e.g. GitHub's full `repo/workflow/write:packages/…` set. There is no "minimal/read-only subset" option; consider a per-server requested-scope override.
- **Health-loop robustness**: per-replica `list_changed` coalescing and the exponential probe backoff are **in-memory** (lost on a registry-api restart → at worst one extra probe of a hard-down server).
